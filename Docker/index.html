Conteneurisation : images, conteneurs, volumes, réseaux et Compose

⚡ En complément du cours 420-TT4-AS

🧠 Concepts essentiels

Image

Modèle figé et immuable (code + OS + dépendances). On la construit avec un Dockerfile, on la distribue via un registre.

Conteneur

Instance exécutable d'une image. Léger, isolé, démarrable/arrêtable. Plusieurs conteneurs peuvent partager une image.

Volumes

Stockage persistant hors du conteneur. La donnée survit aux suppressions de conteneurs.

Réseau

Permet aux conteneurs de communiquer entre eux par nom de service, isolés de la machine hôte par défaut.

Architecture en couches

Votre application (Node, React, API…) ⇩ installée DANS une image (ex. node:22-alpine, postgres:16-alpine, redis:7-alpine) ⇩ lancée comme un conteneur (isolé, port exposé si besoin) ⇩ orchestrée par Docker Compose (plusieurs conteneurs qui collaborent)
⚠️ Conteneur ≠ machine virtuelle : un conteneur partage le noyau de l'hôte. Il est beaucoup plus léger et démarre en secondes. Les données du système de fichiers d'un conteneur sont ÉPHÉMÈRES.

📦 Commandes de base (conteneurs)

# Lancer un conteneur Nginx sur le port 8080 docker run -d --name mon-nginx -p 8080:80 nginx # Options fréquentes -d # détaché (en arrière-plan) --name x # nom du conteneur -p hote:cont # mappage de ports -it # interactif + terminal (pour exec) --restart always # redémarre automatiquement # Gestion du cycle de vie docker ps # conteneurs actifs docker ps -a # tous (même arrêtés) docker stop mon-nginx # arrêt propre docker start mon-nginx # redémarrage docker restart mon-nginx # redémarrage rapide docker rm mon-nginx # suppression DÉFINITIVE docker rm -f mon-nginx # suppression forcée

Inspecter et entrer dans un conteneur

# Logs docker logs mon-nginx docker logs --follow mon-nginx # live # Entrer dans le conteneur (shell) docker exec -it mon-nginx bash # Exécuter une commande ponctuelle docker exec mon-nginx ls /usr/share/nginx/html # Informations détaillées docker inspect mon-nginx docker port mon-nginx # ports exposés docker stats # CPU / mémoire
💡 Pourquoi les modifications disparaissent après docker rm ? Parce que le système de fichiers du conteneur est éphémère. Pour conserver des données, utilisez des volumes (section « Volumes »).

🖼️ Images & Dockerfile

Gérer les images

docker images # liste locale docker pull node:22-alpine # télécharge depuis Docker Hub docker rmi mon-image # supprime une image docker build -t mon-app . # construit depuis le Dockerfile docker tag mon-app myuser/mon-app:1.0 # étiquette (version)

Un Dockerfile pas à pas (application Node.js)

FROM node:22-alpine # image de base alpine (légère) WORKDIR /app # répertoire de travail COPY package.json package-lock.json ./ # d'abord les dépendances RUN npm ci # install propre (cache de couche = rapide) COPY . . # ensuite le code source EXPOSE 3000 # documente le port (port d'exposition) CMD ["node", "server.js"] # commande au démarrage
💡 Ordre des couches = performance : chaque ligne crée une couche. On copie package.json AVANT le code pour que Docker réutilise la couche « npm ci » tant que les dépendances ne changent pas → builds plus rapides.

Multi-stage build (recommandé)

FROM node:22-alpine AS build WORKDIR /app COPY package.json package-lock.json ./ RUN npm ci COPY src ./src COPY tsconfig.json ./ RUN npx tsc # compile TypeScript → dist FROM node:22-alpine # image d'exécution minimale WORKDIR /app COPY --from=build /app/dist ./dist COPY package.json ./ RUN npm ci --omit=dev ENV NODE_ENV=production EXPOSE 3000 CMD ["node", "dist/server.js"]

.dockerignore — ne pas embarquer l'inutile

node_modules dist .env *.log .git .gitignore

💾 Volumes & persistance

Volume nommé (recommandé)

# Dockerfile : /var/lib/postgresql/data est le dossier de données de PG docker volume create pgdata docker run -d --name db \ -v pgdata:/var/lib/postgresql/data \ -e POSTGRES_DB=app -e POSTGRES_USER=app -e POSTGRES_PASSWORD=app \ postgres:16-alpine # 💥 Supprimer le conteneur… les données survivent docker rm -f db docker run -d --name db2 -v pgdata:/var/lib/postgresql/data # … données intactes !

Bind mount (dossier local)

# Partage un dossier de la machine hôte (très utile en dev) docker run -d -v /chemin/local:/app -p 3000:3000 mon-app # Avec un chemin relatif PowerShell : docker run -d -v ${PWD}:/app -p 3000:3000 mon-app
TypeOù vivent les donnéesUsage
Volume nomméGéré par DockerBase de données (production)
Bind mountDossier de l'hôteDéveloppement, rechargement live
tmpfsMémoire RAMDonnées temporaires sensibles
⚠️ docker compose down -v supprime les volumes ! Utilisez -v seulement si vous voulez TOUT purger (base de données incluse).

🔗 Réseaux Docker

# Créer un réseau bridge docker network create app-network # Lancer des conteneurs sur ce réseau docker run -d --name db --network app-network postgres:16-alpine docker run -d --name api --network app-network -p 3000:3000 mon-app # L'API parle à la BDD par SON NOM, pas par IP : # postgres://app:app@db:5432/app docker network ls # lister docker network inspect app-network # voir les membres
💡 Résolution DNS intégrée : sur un même réseau bridge, chaque conteneur est joignable par son nom de service. C'est exactement comme ça que db, redis ou api se retrouvent dans vos URL de connexion.

Exposer des ports

-p 3000:3000 # hôte:conteneur -p 8081:8080 # adminer sur 8081 -P # ports aléatoires publiés # Attention : les conteneurs d'une app interne (db) n'ont PAS besoin de ports exposés

🐙 Docker Compose — la stack complète

Compose orchestre plusieurs conteneurs dans un seul fichier YAML. Un network par défaut relie tous les services, qui se joignent par nom de service.

version: '3.8' services: api: build: . ports: - "3000:3000" environment: DATABASE_URL: postgres://app:app@db:5432/app REDIS_URL: redis://redis:6379 depends_on: db: condition: service_healthy db: image: postgres:16-alpine environment: POSTGRES_DB: app POSTGRES_USER: app POSTGRES_PASSWORD: app volumes: - pgdata:/var/lib/postgresql/data healthcheck: test: ["CMD-SHELL", "pg_isready -U app -d app"] interval: 5s timeout: 5s retries: 5 redis: image: redis:7-alpine healthcheck: test: ["CMD", "redis-cli", "ping"] interval: 5s timeout: 3s retries: 5 adminer: image: adminer ports: - "8081:8080" depends_on: - db volumes: pgdata:

Commandes Compose

docker compose up -d # démarre en arrière-plan docker compose up --build # reconstruit les images docker compose down # arrête tout docker compose down -v # ⚠️ arrête + supprime les volumes docker compose ps # état des services docker compose logs -f api # logs en direct d'un service docker compose exec db psql -U app -d app # SQL interactif docker compose restart api
👉 Pattern d'or : créez l'environnement de dev complet (API + PostgreSQL + Redis + Adminer) avec un seul docker compose up -d, que tout le monde partage. C'est votre terrain de TP3/TP4.

🩺 Healthcheck & débogage

Healthcheck (dépendances saines)

# Le service api attend que db soit « healthy », pas juste « démarré » depends_on: db: condition: service_healthy # État de santé des services docker compose ps # Test manuel d'une image docker run --rm postgres:16-alpine pg_isready -h localhost

Débuguer comme un pro

# 1. Logs docker logs --tail 50 mon-app docker logs -f mon-app # 2. Inspecter le conteneur docker inspect mon-app | grep -i network # 3. Entrer dedans et tester docker exec -it api sh curl http://db:5432 # 4. Vérifier la connectivité réseau docker network inspect app-network
⚠️ Port déjà utilisé ? « port is already allocated » → un autre conteneur occupe le port. Trouvez : docker ps ou netstat -ano | findstr :3000.
