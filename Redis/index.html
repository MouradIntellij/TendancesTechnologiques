💡 À quoi ça sert ? Cache de réponses, sessions, files d'attente, compteurs, classements. On garde en Redis ce qui est fréquent mais pas forcément critique (qui peut être rechargé depuis PostgreSQL).

📄 Les chaînes (Strings) — le type de base

127.0.0.1:6379> SET user:42 "luc" # → OK GET user:42 # → "luc" GET inexistant # → (nil) EXISTS user:42 # → 1 (vrai) DEL user:42 # → 1 (nombre de clés supprimées) SETNX user:42 "luc" # → 1 seulement si NON existante (SET if Not eXists) # Compteurs / incrémentation (atomique !) INCR compteur:vues # → 1, puis 2, 3… INCRBY stock:10 5 # incrémente de 5 DECR compteur:vues # décrémente
👉 Convention de nommage : séparateur : et clé structurée — produit:42, session:abc123, cache:produits:rupture comme si vous aviez un mini-système de « tables ».

🗂️ Les autres types de données

Hashes (dict)

Un objet : une clé → plusieurs champs/valeurs. Parfait pour une entité (produit, user).

Lists

File ordonnée : messages récents, historique, queue FIFO.

Sets

Collection unique, non ordonnée : tags, abonnés, membres.

Sorted Sets

Collection triée par un score : classements, leaderboards.

--- HASH : un objet produit --- HSET produit:10 nom "Laptop" prix 999 stock 5 HGET produit:10 nom # → "Laptop" HGETALL produit:10 # tous les champs HINCRBY produit:10 stock -1 # décrémente le stock de 1 --- LIST : notifications récentes --- LPUSH notifs:42 "commande livrée" # empile à gauche LRANGE notifs:42 0 -1 # tout lister LLEN notifs:42 # longueur --- SET : tags de tags uniques --- SADD tags "ia" "web" "docker" SMEMBERS tags # les membres SISMEMBER tags "ia" # → 1 --- SORTED SET : classement des formations --- ZADD classement 98 "luc" 87 "maya" 92 "sami" ZRANGE classement 0 -1 REV # du plus haut au plus bas ZSCORE classement "maya" # → 87

⏱️ L'expiration (TTL) — le cœur du cache

SET cache:produits "...json..." EX 300 # expire après 300 s # Ou avec une commande séparée : SET cache:produits "...json..." EXPIRE cache:produits 300 # Vérifier / enlever l'expiration TTL cache:produits # secondes restantes (-1 = jamais, -2 = n'existe pas) PERSIST cache:produits # enlève le TTL SET cache:produits ".." KEEPTTL # set sans changer le TTL
⚠️ Pourquoi un TTL ? Sans TTL, les clés de cache s'accumulent sans fin et Redis finit par sortir des données selon la politique d'éviction. Un cache avec TTL = données toujours assez fraîches + mémoire maîtrisée.

🧩 Patterns de cache

Cache-Aside (le plus courant : on lit d'abord le cache)

// GET /api/produits/en-rupture async function produitsEnRupture() { const KEY = 'cache:produits:en-rupture'; // 1. Lire le cache const cached = await redis.get(KEY); if (cached) { return JSON.parse(cached); // ✅ cache HIT } // 2. Cache MISS → aller en base const rows = await pool.query( `SELECT id, nom, prix FROM produits WHERE stock = 0 ORDER BY nom` ); // 3. Remplir le cache avec un TTL await redis.setEx(KEY, 60, JSON.stringify(rows.rows)); return rows.rows; }

Invalidation : on efface le cache quand on écrit en base

async function supprimerProduit(id) { await pool.query('DELETE FROM produits WHERE id = $1', [id]); // 🔥 Invalidation ciblée : la clé du détail du produit await redis.del(`cache:produit:${id}`); // 🔥 + la liste affichée (une invalidation de liste = simple) await redis.del('cache:produits:en-rupture'); }
PatternPrincipeQuand ?
Cache-AsideOn lit cache → sinon base → on remplitLectures fréquentes (listes, détails)
Write-ThroughOn écrit base + cache ensembleDonnées très lues après écriture
Stampede / Thundering HerdÉviter que 100 clients refassent la même requête DB au MISSClés populaires qui expirent
⚠️ Invalidation = SUJET D'EXAMEN : un cache « non invalidé » renvoie des données périmées. Règle : à chaque write DB qui impacte une vue, effacez la clé correspondante.

🔑 Sessions utilisateur

// Au login : créer la session const sessionId = crypto.randomUUID(); await redis.setEx( `session:${sessionId}`, // clé 3600, // 1 heure d'expiration JSON.stringify({ userId: user.id, role: user.role }) ); res.cookie('session', sessionId, { httpOnly: true }); // À chaque requête protégée : const data = await redis.get(`session:${sessionId}`); if (!data) return res.status(401).json({ error: 'Session expirée' }); // Au logout : await redis.del(`session:${sessionId}`);
💡 Pourquoi Redis pour les sessions ? Les sessions HTTP sont volatiles et distribuées : aucun besoin de PostgreSQL (données durables) ; Redis est idéal pour du temporaire rapide + le TTL gère l'expiration automatiquement.

🔌 Client Node.js (redis npm)

npm install redis
import { createClient } from 'redis'; import dotenv from 'dotenv'; dotenv.config(); export const redis = createClient({ url: process.env.REDIS_URL }); await redis.connect(); redis.on('error', err => console.error('Redis error:', err)); // Méthodes principales (équivalent des commandes) await redis.set('cle', 'valeur'); await redis.setEx('cle', 60, 'expire dans 60s'); await redis.get('cle'); // → "valeur" | null await redis.del('cle'); await redis.incr('compteur'); await redis.ttl('cle'); // → secondes restantes await redis.hGetAll('produit:10'); await redis.lRange('notifs:1', 0, -1); await redis.flushDb(); // 🚨 vide tout (dev only)
⚠️ Rappel Docker : URL redis://redis:6379 dans le réseau Compose, redis://localhost:6379 depuis l'hôte. Toujours lire depuis .env.
